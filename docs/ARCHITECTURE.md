# Tavern Dice 架构

扩展围绕当前聊天中的一场战斗工作：正文场景 → 参战数据 → 行动决策 → 本地结算 → 存档与主动发送结果。

## 运行流程

1. 用户通过战斗页、`/dice-init` 或 `/dice-roll start` 触发场景生成。
2. `startBattleByScene()` 把场景指令写入聊天输入框并发送，在发送前注册生成结束等待。
3. 入口的 `GENERATION_ENDED` 监听调用 `_notifyGenerationEnded()`，使等待中的开战流程继续读取正文回复。
4. 场景解析与结构化流程提取当前参战者、属性、技能、装备和临时状态，形成当前场景数据。
5. 应用已选自定义技能与装备，战斗引擎初始化单位与先攻并等待玩家提交行动；随后按先攻处理前置AI和本次行动，打开界面或换人不自行推进。
6. 本地引擎根据规则集、状态和随机数计算命中、伤害、资源与回合变化。
7. 保存战斗状态；用户主动发送结算结果给正文模型继续叙事。

读取已有场景和只写指令模式保留。结构化或决策调用属于战斗过程，不由普通消息接收、编辑、删除或 swipe 自动触发。

## 模型边界

正文模型理解当前场景，结构化 API 将场景变成可校验的数据。战斗决策 API 提供技能与目标选择；它不负责决定骰点、命中或最终伤害。

战斗模型的连接沿用内部 `p2.channel` 键。UI 使用「战斗模型」名称。配置迁移应把旧战斗选择中的 `p1` 转为 `p2`，并保留有效连接参数。

## 数据与规则

`powerSystem` 兼容字段承载当前场景数据。战斗运行时以 `battle.units` 为实时状态，状态命令优先显示这些单位；没有战斗时回退到当前场景的 `combatants`。

用户规则覆盖优先，其次使用可用的场景规则，最后使用通用 d20。规则公式作为数据解析；机械结算使用带种子的随机数。同样的初始状态、规则、随机数状态与行动序列产生一致的机械结果。

## 事件与聊天隔离

- `GENERATION_ENDED`：通知正在等待的场景生成流程。
- `CHAT_CHANGED`：先停止自动推进，释放当前战斗引用，再恢复目标聊天的战斗并刷新界面。
- `SETTINGS_UPDATED`：同步界面偏好。
- `APP_READY`：补充刷新挂载的面板。

普通消息事件不修改场景参战数据。聊天切换后的异步结果必须避免写入错误的聊天；有关任务取消和归属检查由控制器管理。

## 存档与正文输出

扩展设置保存在 `ctx.extensionSettings`；场景、战斗快照与审计数据保存在当前聊天的 `ctx.chatMetadata`。战斗快照保存规则、单位、回合、日志与随机数状态，供恢复使用。

每回合的计算显示在插件中。场景与自定义库润色通过原生聊天发送及生成完成等待；成功保存后由 `loadout-chat.js` 校验身份、楼层内容和生成活动，尝试删除本次请求与回复两楼。结算通过原生发送触发续写，不自动清理。导入存档保持本机连接配置；头像保存在本机 IndexedDB，未包含于聊天导出。

## 验证重点

运行 `npm run verify` 检查模块加载、单元测试和启动冒烟。重点覆盖：场景生成完成信号、取消与超时、解析失败、决策失败、确定性结算、存档恢复、聊天切换以及结果发送。
